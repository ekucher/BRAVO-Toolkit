# Розкатка BRAVO-Toolkit 5.2.4 по парку — операторський runbook

Дата: 2026-09-13. Цільова версія: **5.2.4** (stable), тег `v5.2.4`,
коміт-stamp `e53bd6b`, `sourceCommit = 91db94c007d770d8897ccaf9743bc36cd2f55e3f`.

Попередня stable — 5.2.3. Перехід 5.2.3 → 5.2.4 не видаляє з комплекту
жодного файлу (додано один документ), тому оновлення виконується
копіюванням поверх.

---

## 1. Що саме змінюється і чому це важливо для розкатки

`MinimumFreeSpaceGB` більше не блокує **архівацію**, якщо місця для самої
операції вистачає. Поріг знову є індикатором здоров'я тому.

**Але `BRAVO_MAINTENANCE` цієї зміни НЕ отримує.** Обслуговування не має
розрахунку потреби, тому для нього поріг лишився жорстким гейтом. Обидві
операції читають **той самий ключ** `maintenanceSettings.Limits.MinimumFreeSpaceGB`.

Практичний наслідок, який і визначає весь порядок нижче: сервер із
порогом, вищим за вільне місце на робочому томі, після оновлення **вдень
успішно архівуватиме, а вночі валитиме обслуговування** з
`BelowFallbackFloorNoEstimate` і `exit 60`. Зв'язок із конфігурацією не
буде очевидним.

Тому крок 2 цього runbook — не формальність, а головна його частина.

---

## 2. Що мати під рукою

| Що | Звідки |
|---|---|
| `Update-BRAVOServer.ps1` | помічник розкатки (проміжний, поза репозиторієм) |
| `BRAVO-Toolkit-5.2.4.zip` + `.sha256` | https://github.com/ekucher/BRAVO-Toolkit/releases/tag/v5.2.4 |
| Права адміністратора на кожному сервері | — |
| Вікно поза нічними завданнями | розклад кожного сервера |

Очікуваний SHA-256 архіву:

```
DDBECEFF5ED5E1AAF77F416AB6CC5CB318E7B8E7AC0BBA98BFF1B19873E66A45
```

Скрипт звіряє його сам; вручну — лише якщо качаєте архів окремо.

`Update-BRAVOServer.ps1` — проміжний помічник розкатки; він навмисно не
входить до комплекту й не покритий `RUNTIME_MANIFEST.json`. Постійну
заміну (`BRAVO_UPDATE.ps1` + `modules/BRAVO.Update/`) заплановано на
5.3.0 — ROADMAP, пункт P3.2a.

Для серверів без доступу до GitHub переносьте **обидва** файли — `.zip` і
`.sha256`. Без файлу контрольної суми скрипт зупиниться і не
розгортатиме.

## 3. Порядок парку

Не розкочуйте все одразу.

```
інвентаризація (крок 1, read-only, усі сервери)
    -> розв'язання блокерів порогу (крок 2)
    -> пілотний сервер (крок 3)
    -> перевірка першої доби на пілоті (крок 4)
    -> решта парку (крок 5)
```

Пілотом беріть сервер, стан якого вам найкраще відомий. Один
production-сервер парку вже пройшов повний acceptance 5.2.4-rc.1 — чотири
прогони архівації і прогін обслуговування.

---

## 4. Крок 1 — інвентаризація (нічого не змінює)

На кожному сервері, з піднятими правами:

```powershell
.\Update-BRAVOServer.ps1 -PreflightOnly
```

Скрипт читає **ефективну** конфігурацію канонічним завантажувачем
(`Import-BravoConfiguration`), тобто враховує `BRAVO.local.config`, і
друкує таблицю по кожному локальному Fixed-диску:

| Стовпець | Що означає |
|---|---|
| `ЄмністьGB` / `ВільноGB` | фактичні цифри тому |
| `ПорігGB` | ефективний `MinimumFreeSpaceGB` |
| `Виключено` | том у `Limits.ExcludedDrives` |
| `ROOT_LIMS` | це робочий том Maintenance (`EffectiveLIMSRoot`) |
| `Вердикт` | `OK`, `НИЖЧЕ ПОРОГУ` або `ПОРІГ ВИЩЕ ЗА ЄМНІСТЬ` |

Занотуйте результат кожного сервера в журнал (розділ 9).

### Як читати вердикт

- **`OK` на всіх томах** — сервер готовий, переходьте далі.
- **Не-`OK` на томі з `ROOT_LIMS = True`** — **блокер**. Скрипт відмовиться
  оновлювати. Це саме той сервер, який зламав би нічне обслуговування.
- **Не-`OK` на іншому томі, не виключеному** — попередження, не блокер.
  Дає `exit 10` і сповіщення в ALERTS на кожному прогоні, але роботу не
  зупиняє.
- **`ПОРІГ ВИЩЕ ЗА ЄМНІСТЬ`** — поріг недосяжний у принципі, скільки місця
  не звільняй.

## 5. Крок 2 — розв'язання блокерів порогу

Робіть це **до** оновлення. Три варіанти, за спаданням переваги.

**А. Звільнити місце на робочому томі.** Найчесніший шлях, якщо поріг
відображає реальну потребу.

**Б. Привести поріг до реалістичного.** Типове значення в `BRAVO.config` —
`20` GB. Якщо на сервері він завищений історично, поверніть через
site-overlay, не правлячи `BRAVO.config`:

```powershell
# <runtime>\BRAVO.local.config
@{
    'maintenanceSettings.Limits.MinimumFreeSpaceGB' = 20
}
```

Файл — data-only hashtable «dot-шлях -> значення». Якщо він уже існує,
**додайте ключ до наявних**, не перезаписуйте файл: там можуть бути
`ExcludedDrives` та інші site-налаштування.

Записуйте його як UTF-8. У PowerShell 5.1 `Set-Content -Encoding UTF8`
додає BOM — завантажувач це переживає, перевірено.

**В. Виключити том.** Лише для томів, які **не** є `ROOT_LIMS`:

```powershell
'maintenanceSettings.Limits.ExcludedDrives' = @('F:\', 'G:\')
```

Пам'ятайте ціну: виключення прибирає **весь** health-моніторинг тому —
заповнений на 100% диск мовчатиме так само, як порожній. І воно **не**
відкриває дорогу запису на том, який операції реально потрібен.

Після правки повторіть крок 1 і переконайтесь, що вердикт став `OK`.

---

## 6. Крок 3 — пілотний сервер

Переконайтесь, що нічні завдання не виконуються і до найближчого лишається
щонайменше година.

```powershell
.\Update-BRAVOServer.ps1
```

Що станеться по порядку: preflight (кроки 1-2 повторюються) → завантаження
і звірка SHA-256 → розпакування в staging → **backup копіюванням** у
`<runtime>.old_<версія>_<час>` → копіювання поверх → гейти.

Гейти після заміни:

1. `VERSION.json` = `5.2.4`;
2. `BRAVO_RUNTIME_GUARD.ps1` → `exit 0`;
3. `BRAVO_SETUP -Action Scheduler` → перереєстрація завдань;
4. `BRAVO_SETUP -ValidateOnly` → `exit 0`.

Провал будь-якого гейта — **автоматичний відкат** з backup і повторна
перевірка guard.

### Якщо guard дасть exit 35

`VersionDowngradeBlocked` — на цій машині раніше запускалась новіша лінія
(наприклад, dev-збірка). Це коректна робота захисту. Якщо пониження
свідоме, повторіть прогін зі встановленою змінною:

```powershell
$env:BRAVO_ALLOW_DOWNGRADE = '1'
```

На production-серверах парку цього зазвичай не потрібно.

---

## 7. Крок 4 — перевірка першої доби на пілоті

Не розкочуйте далі, доки не побачите **обидві** нічні операції.

Наступного ранку перевірте свіжі логи в `<runtime>\LOGS`:

```powershell
Get-ChildItem "$env:ProgramFiles\BRAVO-Toolkit\LOGS" -Filter 'BRAVO_*.log' |
    Sort-Object LastWriteTime -Descending | Select-Object -First 5 Name, LastWriteTime
```

**Архівація** — у `BRAVO_ARCHIV_*.log`:

- `=== ПОЧАТОК РОБОТИ СКРИПТА BRAVO_ARCHIV v.5.2.4 ===`;
- `Generation <id>: COMPLETE (опубліковано 3 з 3)`;
- `Завантажено 7 з 7 файлiв на SFTP`;
- `Результат: УСПIШНО`.

**Обслуговування** — у `BRAVO_MAINTENANCE_*.log`:

- `СТАТУС: УСПІШНО`;
- **не** `BelowFallbackFloorNoEstimate`.

Якщо в лозі архівації бачите `Status=Warning` з
`BelowHealthFloorButRequirementSatisfied` і `Blocks=False` — це **штатно**
для 5.2.4: поріг нижче вільного місця, але потреба задоволена, прогін
дозволено, код завершення 10.

Якщо бачите `BelowFloorEstimateNotPeakSafe` — оновлення не застосувалось,
сервер працює на 5.2.3. Перевірте `VERSION.json`.

### Коди завершення

| Код | Значення | Дія |
|---|---|---|
| 0 | успіх | — |
| 10 | `SuccessWithWarnings` | подивитись попередження, роботу не зупиняє |
| 33 | `RuntimeIntegrityViolation` | комплект пошкоджено, відкат |
| 35 | `VersionDowngradeBlocked` | див. розділ 6 |
| 40 | `LocalArchiveFailed` | розібрати рядки `DiskSpace` у лозі |
| 60 | `MaintenanceFailed` | найімовірніше поріг — див. розділ 5 |

---

## 8. Крок 5 — решта парку

Повторіть кроки 3-4 для кожного сервера. Розумний темп — не більше
двох-трьох серверів за вечір, щоб кожен встиг показати нічний прогін.

Backup-каталоги **не видаляються автоматично**. Прибирайте
`<runtime>.old_*` лише після успішної доби на тому сервері.

## 10. Відкат

**Автоматичний** — виконується самим скриптом при провалі гейта.

**Ручний**, якщо проблему виявлено пізніше:

```powershell
$runtime = 'C:\Program Files\BRAVO-Toolkit'
$backup  = 'C:\Program Files\BRAVO-Toolkit.old_5.2.3_20260913_190000'   # свій шлях

Get-ScheduledTask -TaskPath '\BRAVO\' | Where-Object State -eq 'Running'   # має бути порожньо
robocopy $backup $runtime /E /R:2 /W:2 /XD LOGS
Push-Location $runtime; .\BRAVO_RUNTIME_GUARD.ps1; $LASTEXITCODE; Pop-Location
```

Guard має дати `0`. Далі `.\BRAVO_SETUP.ps1 -Action Scheduler` для
повернення визначень завдань попередньої версії.

**Не перейменовуйте каталог runtime** ні при оновленні, ні при відкаті.
ACL-захист `BRAVO_TASKS_INSTALL` забороняє це навіть адміністратору;
спроба rename+move кладе новий комплект усередину старого і валить нічні
завдання guard-ом з кодом 33. Це реальні граблі з розкатки v5.1.0.

---

## 11. Що оновлення не чіпає

Зберігаються без змін: `BRAVO.config`, `BRAVO.local.config`,
`Tools\TOOLS_INTEGRITY.json` (TOFU-базова лінія сервера), `WinSCP.ini`,
`LOGS\` і каталоги призначення бекапів (`MODEL\`, `BLOG\`, `BRAVOEXCH\`,
`BAZA\`, `BAZA_WWW\`, якщо вони лежать у корені комплекту).

Жоден файл з runtime не видаляється.

---

## 12. Відомі обмеження 5.2.4

Заплановано на 5.3.0, специфікація —
`docs/BRAVO_530_DISK_SPACE_HEALTH_SIGNAL_TASK.md`.

1. **Том, менший за поріг за повною ємністю, попереджає вічно.** Закрити
   дією оператора неможливо; обхід — `ExcludedDrives` з відомою ціною.
2. **Лічильник `Попереджень` у підсумку Maintenance не бачить попереджень
   preflight.** Можливий `Попереджень: 0` поруч із `exit 10` — підсумок
   суперечить коду завершення.
3. **Зведений операторський рядок рішення приписує всім шляхам тому
   причину першої entity.** Джерелом істини лишається структурований
   рядок `DiskSpace StorageKind=... Reason=...` — він правдивий по кожній
   entity окремо.
4. **Асиметрія Archive/Maintenance** — розділ 1 цього документа.

Жодне з чотирьох не впливає на коректність рішення, цілісність даних чи
exit-коди.
