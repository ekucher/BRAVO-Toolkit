# 5.3.0 — peak-safe оцінка місця і повернення below-floor relaxation

Статус: **специфікація, до реалізації**. Заведено за результатами acceptance
5.2.3-rc.6 (13.09.2026, `docs/BRAVO_523_RC6_ACCEPTANCE_EVIDENCE_20260913.md`,
розділ 4.5).

> **Передумова.** Гілка `developer` ще не містить модуля `BRAVO.DiskSpace` —
> уся operation-aware disk-space робота живе в лінії 5.2.3 і потрапить сюди
> зі sync-ом за `RELEASE_POLICY.md` §12.2. До того моменту посилання на файли
> й рядки нижче стосуються `hotfix/5.2.3` (коміт `f861f30`) і на `developer`
> не резолвляться. Реалізацію цієї задачі починати ПІСЛЯ §12.2 sync.

## 1. Проблема

`MinimumFreeSpaceGB` блокує архівацію на томі призначення навіть тоді, коли
місця для самої операції вистачає з величезним запасом.

Відтворено на `LIMS-TOP` 13.09.2026 04:57 (журнал
`BRAVO_ARCHIV_20260913_045706_PID8236.log`):

```text
AvailableGB=715.46  AggregatedRequiredGB=0.0686  MinimumFreeSpaceGB=730
Status=Error Blocks=True Reason=BelowFloorEstimateNotPeakSafe
Код завершення: 40 — LocalArchiveFailed
```

Операція потребувала 0.07 GB при 715 GB вільного — і була заблокована, бо
вільне виявилось нижчим за поріг. Поріг тут працює не як захист операції, а
як паушальне правило «на диску має бути N GB», застосоване до рішення, якого
воно не стосується.

У 5.2.1 такий вхід проходив: `Merge-BRAVOArchiveSpaceCheckResults` надавав
below-floor relaxation, якщо оцінка достатня. У 5.2.3 послаблення свідомо
вимкнено (рішення reviewer #2 від 30.08.2026,
`modules/BRAVO.Archive/BRAVO.Archive.Runtime.ps1:5558-5566`), і це
задокументовано в CHANGELOG 5.2.3 як посилення політики.

Мета 5.3.0 — повернути послаблення, але **на підставі оцінки, якій можна
довіряти**, а не скасуванням захисту.

## 2. Поточний стан коду

### 2.1. Де ухвалюється рішення

`Resolve-BRAVODiskSpaceGroupDecision`
(`modules/BRAVO.DiskSpace/BRAVO.DiskSpace.psm1:749-763`):

```powershell
if ($aggregated -gt $available) {
    $groupReason = 'EstimatedRequirementNotMet'          # блокує завжди
} elseif ($available -lt $floor) {
    if ($RequirementPolicy -eq 'ArchiveNotPeakSafe') {
        $groupReason = 'BelowFloorEstimateNotPeakSafe'   # блокує
    } else {
        $groupReason = 'BelowHealthFloorButRequirementSatisfied'  # WARNING + ALLOW
    }
}
```

Обидві гілки вже реалізовані й покриті self-test: `Archive/A24` (блокує під
`ArchiveNotPeakSafe`) і `Archive/A25` (той самий вхід під `ArchivePeakSafe`
дає ALLOW + WARNING). Production-виклик жорстко задає
`RequirementPolicy = 'ArchiveNotPeakSafe'`
(`BRAVO.Archive.Runtime.ps1:5641`).

Тобто **сам механізм послаблення вже є**. Бракує лише підстави ним
скористатись.

### 2.2. Як рахується оцінка

`Get-BRAVOArchiveEstimatedSpaceRequirement`
(`BRAVO.Archive.Runtime.ps1:5453-5454`):

```powershell
$lastBytes = [int64]$history[0].Bytes
$estimatedBytes = [int64][math]::Ceiling($lastBytes * (1.0 + ($MarginPercent / 100.0)))
```

Розмір останнього hash-підтвердженого архіву компонента, помножений на
`1 + MarginPercent/100` (за замовчуванням 25%). Компонент без валідної
історії свідомо виключається з оцінки — `HasHistory=false`, група переходить
у `GroupRequirementState=Unknown` з окремим fallback.

## 3. Що треба перевірити перед реалізацією (Phase 0)

Обґрунтування в коді (рядки 5559-5562) називає причиною не-peak-safety
«retained generations і `.work` тимчасові файли». Уважне читання рушія цю
пару під сумнів ставить, і специфікацію не можна будувати на неперевіреному
припущенні:

- **`.work`.** `New-BRAVOTemporaryArchivePath` (рядок 2784) створює
  `<Destination>\.work\<name>.<guid>.partial<ext>` — той самий том, а
  публікація є перейменуванням, не копіюванням (коментар рядка 2775-2777).
  Отже `.work` у піку тримає рівно один розмір архіву, який оцінка вже
  враховує, а не подвоює вимогу.
- **Retained generations.** Retention архівів (`archiveRetentionDays = 183`,
  `BRAVO.config:478`) виконується ПІСЛЯ backup. Але наявні генерації вже
  лежать на диску на момент вимірювання, тобто вже враховані у
  `AvailableGB`. Приріст піку — це рівно нова генерація.

Тому Phase 0 має **заново охарактеризувати пік** і встановити, які саме
споживачі місця оцінка не покриває. Кандидати до вимірювання:

1. **Зростання джерела між прогонами.** Оцінка ретроспективна: 25% запасу —
   евристика. Якщо MODEL виріс на 40% з попереднього архіву, оцінка коротка.
   Потрібен розподіл фактичного приросту по парку за наявними журналами.
2. **VSS diff area.** Тіньова копія тримає область різниць на самому томі.
   Для `D:` це той самий том, що й призначення. Обсяг залежить від запису в
   джерело під час архівації і в оцінці не фігурує взагалі.
3. **Компоненти без історії.** `HasHistory=false` виключає компонент з
   оцінки повністю. Для bootstrap це свідоме рішення, але воно означає, що
   `AggregatedRequiredGB` може бути суттєво заниженим саме тоді, коли
   передбачити споживання найважче.
4. **Паралельні споживачі.** Maintenance тримає спільний
   `BRAVO_OPERATION.lock`, тож конкуренції з ним немає; перевірити, чи є
   інші процеси, що пишуть у `D:\LIMS\ARCHIV` під час backup (ротація
   Trace, exchangAPI).

Результат Phase 0 — документ із виміряним піком і формулою, що його
покриває. Без нього перемикати політику не можна: це замінить одну
недоведену підставу на іншу.

## 4. Обсяг робіт

### 4.1. Peak-safe оцінка

Розширити `Get-BRAVOArchiveEstimatedSpaceRequirement` так, щоб
`EstimatedBytes` був **верхньою межею** піку, а не проєкцією останнього
розміру. Мінімум:

- врахувати виміряні в Phase 0 складові (VSS diff area, приріст джерела за
  фактичним розподілом, а не фіксованими 25%);
- для `HasHistory=false` замість виключення з оцінки повертати
  консервативну верхню межу з розміру джерела, залишивши поточну
  `Unknown`-гілку лише для випадку, коли й джерело виміряти не вдалося;
- зберегти injectable `-Drives` для детермінованого self-test.

Нову поведінку відобразити в полі результату — щоб `GroupRequirementState`
розрізняв «оцінка peak-safe» і «оцінка є, але лише нижня межа».

### 4.2. Перемикання політики

`BRAVO.Archive.Runtime.ps1:5641` — `'ArchiveNotPeakSafe'` на
`'ArchivePeakSafe'`. Один рядок, але робити його можна лише після 4.1: без
peak-safe оцінки це просто зняття захисту.

### 4.3. Том, менший за поріг

Суміжний борг, зафіксований в evidence 5.2.3 §8. `G:` на `LIMS-TOP` має
15 GB загальної ємності при порозі 20 GB, тобто дає health-попередження
завжди й невиправно. Обходиться внесенням у `ExcludedDrives`, але це
приховує том від моніторингу цілком.

Пропозиція: коли `TotalGB < MinimumFreeSpaceGB`, поріг для health-оцінки
цього тому має вироджуватись у частку ємності (наприклад 10%), а не
застосовуватись буквально. Окрема `Reason`, щоб рішення було видно в
журналі.

Це та сама хвороба, що й основна задача: глобальний поріг застосовується
там, де він не має сенсу. 5.2.3 навчив систему розрізняти ролі томів;
5.3.0 має навчити її розрізняти справжню потребу від паушального порога.

### 4.4. Лічильник попереджень

Ще один пункт з evidence 5.2.3 §8: у підсумку Maintenance `Попереджень: 0`
не враховує попередження з передетапної перевірки місця (виявлено на rc.3,
коли exit був 10). Після зміни політики below-floor стане штатним
джерелом WARNING, тож розбіжність лічильника з кодом завершення почне
траплятися регулярно — полагодити разом.

## 5. Зміни в self-test

| Серія | Зараз | Після |
|---|---|---|
| `Archive/A24` | below-floor з достатньою оцінкою БЛОКУЄ | ALLOW + WARNING `BelowHealthFloorButRequirementSatisfied` |
| `Archive/A25` | той самий вхід під `ArchivePeakSafe` дозволяє | зливається з A24; звільнене місце — під нову негативну серію |
| нова | — | peak-safe оцінка НЕ влазить у доступне → BLOCK `EstimatedRequirementNotMet` |
| нова | — | `HasHistory=false` з вимірюваним джерелом → консервативна верхня межа, не `Unknown` |
| нова | — | `TotalGB < MinimumFreeSpaceGB` → вироджений поріг, окремий `Reason`, не вічне попередження |

Серії `DiskSpace/S5`, `S13`, `S15d` (блокування `EstimatedRequirementNotMet`
і `ExclusionIgnoredForRequiredVolume`) змінюватись не повинні — вони
перевіряють гілку, яку ця задача не чіпає. Якщо якась із них падає після
змін, це регресія, а не очікуване оновлення.

## 6. Критерії приймання

1. Phase 0 задокументовано: виміряний пік і формула, що його покриває.
2. Self-test зелений, включно з новими серіями; жодна з `DiskSpace/S*` не
   змінена «під результат».
3. На реальному сервері відтворено сценарій, дзеркальний до 4.5 evidence
   5.2.3: `available < floor`, оцінка достатня — прогін **проходить** з
   WARNING, а не блокується. Журнал містить
   `Reason=BelowHealthFloorButRequirementSatisfied`.
4. Там же відтворено протилежний випадок: peak-safe оцінка не влазить —
   прогін блокується з `EstimatedRequirementNotMet`. Захист не втрачено.
5. `ExclusionIgnoredForRequiredVolume` продовжує спрацьовувати на
   блокувальних рішеннях (перевірка з розділу 4.5 evidence 5.2.3
   повторюється без змін очікувань).
6. Том, менший за поріг, не дає вічного попередження і при цьому лишається
   під моніторингом (не через `ExcludedDrives`).
7. CHANGELOG 5.3.0 описує повернення послаблення як зміну політики з
   посиланням на 5.2.3, де воно було вимкнене — щоб історія рішення
   читалась в обидва боки.

## 7. Що НЕ входить

- Зміна `MinimumFreeSpaceGB` за замовчуванням (20 GB) — це site-рішення.
- Скасування `ExcludedDrives` або зміна їхньої семантики: виключення й далі
  не сміє відкривати дорогу запису на том, де місця бракує.
- Будь-яка зміна `EstimatedRequirementNotMet` — ця гілка лишається жорстким
  блокуванням.
