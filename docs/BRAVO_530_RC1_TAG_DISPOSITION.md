# Доля тега `v5.3.0-rc.1` — аналіз і рекомендація

Дата аналізу: 2026-09-16. База: `developer` `b9bd4dc`, `master` `f8fa5aa`.

Документ **тільки читання**: жодної дії над тегами, релізами чи
`VERSION.json` за ним не виконано. Мета — встановити, чим насправді є
тег `v5.3.0-rc.1`, і що з ним робити перед наступним кандидатом циклу
5.3.0.

чого** ухвалювались рішення. Але між написанням і мержем усі чотири
знахідки вже закрито, тому читати їх як перелік відкритих проблем не
треба.

## Короткий висновок

**З самим тегом не робити нічого.** Він коректний, незмінний і є
правдивим записом кандидата, який не пройшов приймання. Наступний
кандидат циклу — `v5.3.0-rc.2`, а не повторне нарізання `rc.1`.

Проблема не в тезі, а в **документації й метаданих, які навколо нього
дрейфували**. Нижче — чотири знахідки, з них одна впливає на кожен
артефакт, зібраний з `developer` починаючи з 2026-08-26.

## 1. Що таке `v5.3.0-rc.1` фактично

Перевірені факти:

| Властивість | Значення |
| --- | --- |
| Тип об'єкта | анотований тег (`git cat-file -t` → `tag`) |
| Коміт | `3a87079` «stamp: 5.3.0-rc.1», 2026-08-26 13:58:31 +0300 |
| `packageVersion` у тезі | `5.3.0-rc.1` |
| `releaseChannel` у тезі | `prerelease` |
| Провенанс у тезі | `buildId=f4351a5`, `sourceCommit=f4351a5…` |
| Предок `developer`? | так (`git merge-base --is-ancestor` → true) |
| Комітів у `developer` після тега | **652** |
| GitHub Release | існує, але **draft** (`GET /releases/tags/v5.3.0-rc.1` → 404; видно лише у списку всіх релізів) |
| Ассети draft-релізу | `BRAVO-Toolkit-5.3.0-rc.1.zip`, `.zip.sha256`, `release-manifest.json` |
| Розділ CHANGELOG | `## 5.3.0-rc.1 — 2026-08-26 (candidate, pending acceptance)` |
| Acceptance-evidence документ | **відсутній** (у `docs/` є evidence лише для 5.2.0-rc.13, 5.2.3-rc.6, 5.2.4-rc.1) |

Повідомлення тега описує scope: dev.1 + P1.1 `BRAVO_RESTORE_VERIFY` +
P2.1 status contract + FIX-пакет deferred-боргів 5.2.0.

**Кандидат ніколи не приймався.** `RELEASE_POLICY.md` §20 фіксує
рішення власника: цикл 5.3.0 свідомо повернуто в development, щоб
внести P0 Configuration Foundation, бо §3.2 забороняє нові функції в
RC. Тобто `rc.1` не «загубився» — його свідомо інвалідовано фічею, як
раніше `5.1.0-rc.1`.

### Чому тег лишається

`RELEASE_POLICY.md` §15.3: «Перезапис опублікованих тегів заборонений».
Issue #151 наразі домагається саме того, щоб це стало механічним
ruleset-ом на `refs/tags/v*` (restrict deletions + restrict updates).
Видалити або зсунути `v5.3.0-rc.1` означало б власноруч зробити те,
проти чого відкрита #151.

Тег до того ж корисний: він робить видимою межу між прийманням циклу
5.3.0 і 652 комітами роботи, що прийшли після нього.

### Що з draft-релізом

Тег незмінний — **ассети ні**. `.github/workflows/release-artifact.yml`
дозволяє `gh release upload --clobber` саме на draft-гілці (ремонтний
шлях), і `RELEASE_POLICY.md` §16.1 це фіксує свідомо. Тому ZIP
`5.3.0-rc.1` не є доказом незмінності — доказом є тег і `sourceCommit`
у ньому. Це не дефект, але про це не можна забувати, якщо колись
знадобиться посилатись на артефакт rc.1.

## 2. Знахідка П1 — `releaseDate` у `developer` заморожено на даті `rc.1`

**Це найвагоміше, і причина саме в `rc.1`.**

`VERSION.json` у `developer` сьогодні:

```json
"packageVersion": "5.3.0-dev.3",
"releaseDate":    "2026-08-26",
"buildId":        "86270a1"
```

Історія поля:

| Штамп | Дата коміту | `packageVersion` | `releaseDate` |
| --- | --- | --- | --- |
| `3a87079` | 2026-08-26 | `5.3.0-rc.1` | `2026-08-26` |
| `42bcb4c` | 2026-09-02 | `5.3.0-dev.2` | `2026-08-26` |
| `c90107c` | 2026-09-03 | `5.3.0-dev.2` (restamp) | `2026-08-26` |
| `36d76c1` | 2026-09-13 | `5.3.0-dev.3` | `2026-08-26` |

Для порівняння, stable-штампи поле оновлюють коректно: `e53bd6b`
(`5.2.4`) має `releaseDate = 2026-09-13`.

**Чому це не косметика.** Поле не є декоративним:

- `BRAVO_CONFIG_LOADER.ps1:102-169` валідує його і віддає як
  `ReleaseDate`, звідки воно потрапляє в `ScriptDate`;
- `BRAVO_SELF_TEST.ps1:3465` вимагає, щоб `VERSION.json` був **єдиним**
  джерелом `ScriptVersion`/`ScriptDate`/`ScriptBuildId`;
- `ci/New-BRAVOReleaseArtifact.ps1:145` переносить його в
  `release-manifest.json` кожного зібраного артефакту.

Отже кожен артефакт, зібраний з `developer` після 2026-08-26, заявляє
дату релізу 2026-08-26. Оператор, який звіряє провенанс за §16.3,
побачить дату, старшу за вміст на три тижні.

**Чому механізм не спрацював.** Жоден скрипт `ci/` поле не записує —
grep дає лише читачів. Воно ведеться вручну, і `ci/Test-BRAVOReleasePolicy.ps1`
його не звіряє (§14.3 перелічує перевірки версії, каналу, CHANGELOG і
маніфестів — дати серед них немає). Це той самий клас дефекту, що
закрила автоматизація parity harness (§14.4): обов'язок без механізму
не виконується.

## 3. Знахідка П2 — `5.3.0-dev.3` не має власного штампу й тега

`packageVersion` став `5.3.0-dev.3` не окремим штамп-комітом, а
**всередині merge-резолюції** `36d76c1` (PR #143, обов'язкова
синхронізація §12.2 після stable 5.2.3). Разом із версією там
збереглися провенанс-поля попереднього кандидата: `buildId = 86270a1` і
відповідний `sourceCommit` — це коміт restamp-у `5.3.0-dev.2`
(`c90107c`, 2026-09-03).

Наслідок: `5.3.0-dev.3` заявляє провенанс `5.3.0-dev.2`. Тега
`v5.3.0-dev.3` не існує — у лінії 5.3 є лише `v5.3.0-rc.1`.

`RELEASE_POLICY.md` §7.2 вимагає для dev-релізу оновити `VERSION.json`,
синхронізувати `ModuleVersion`, оновити `CHANGELOG.md`, перегенерувати
маніфести й поставити тег. Розділ CHANGELOG для `5.3.0-dev.3` існує
(рядок 1206, дата 2026-09-13), решти кроків немає.

Тобто `5.3.0-dev.3` — це **робоча позначка лінії розробки, а не
випущений dev-реліз**. Це припустимо (§5.3 вимагає лише форму
`X.Y.Z-dev.N` і канал `development`, і CI на `b9bd4dc` зелений), але
провенанс у пакеті вводить в оману, і перед `rc.2` його треба
переставити свідомо.

## 4. Знахідка П3 — `RELEASE_POLICY.md` §20 відстає на чотири stable-релізи

§20 «Поточний стан» заявляє:

```text
master:    5.2.0
developer: 5.3.0-dev.2
```

Фактично:

```text
master:    5.2.4   (тег v5.2.4, реліз опубліковано 2026-09-13)
developer: 5.3.0-dev.3
```

Пропущені в §20 stable-релізи: `5.2.1` (2026-08-28), `5.2.2`
(2026-08-30), `5.2.3` і `5.2.4` (обидва 2026-09-13).

Опис наступного кандидата в §20 («rc.2 включатиме й dev.1, і новий P0
Configuration Foundation») теж застарів на 652 коміти: після нього в
`developer` з'явилися `BRAVO_CONFIGURATOR`, presence-driven discovery,
DataRestore matrix, уся серія Configuration v2 і вибірковий self-test.

`RELEASE_POLICY.md` §9.3 називає критерієм готовності RC те, що
«документація відповідає фактичній поведінці». §20 цьому критерію
сьогодні не відповідає, і механічного гейта на нього немає — на відміну
від §13.3, який звіряється guard-ом
`Governance/RequiredChecksListCoversCiWorkflowJobs`.

## 5. Знахідка П4 (низький пріоритет) — `deploy/README.md` як приклад бере неприйнятого кандидата

`deploy/README.md:103`:

```powershell
.\Update-BRAVOServer.ps1 -Tag v5.3.0-rc.1 -AllowPrereleaseChannel
```

Це ілюстрація свідомого розгортання prerelease, а не інструкція, і
поведінка гейта описана поруч коректно. Але як приклад для копіювання
взято рівно того кандидата, який приймання не проходив, а його
GitHub Release лишається draft-ом — тобто за цим тегом артефакт
завантажити не вийде. Приклад варто замінити на нейтральний
(`vX.Y.Z-rc.N`) або на реально опублікований prerelease
(`v5.2.3-rc.6`).

## Рекомендація

Порядок дій перед нарізанням `v5.3.0-rc.2`:

1. **Тег `v5.3.0-rc.1` не чіпати.** Не видаляти, не зсувати, не
   перевикористовувати номер. Наступний кандидат — `rc.2`.
2. **Draft-реліз `v5.3.0-rc.1` не публікувати.** Кандидат не приймався;
   публікація зробила б доступним для розкатки артефакт без приймання.
   Видаляти теж не обов'язково — draft нікому не видимий і не заважає.
3. **Полагодити `releaseDate` (П1)** окремою зміною, до будь-якого
   штампування `rc.2`: поле має відповідати штампу, а не залишку від
   `rc.1`. Разом з тим варто додати звірку в
   `ci/Test-BRAVOReleasePolicy.ps1`, інакше поле поїде знову.
4. **Переставити провенанс лінії (П2)** свідомим штамп-комітом, а не
   merge-резолюцією; вирішити при цьому, чи `5.3.0-dev.3` оголошується
   dev-релізом за §7.2 (штамп + тег + маніфести), чи лишається робочою
   позначкою — і записати рішення.
5. **Актуалізувати §20 (П3)** під фактичний стан: `master` 5.2.4,
   `developer` 5.3.0-dev.3, хронологія 5.2.1-5.2.4, реальний scope
   майбутнього `rc.2`. Окремо варто зважити механічний guard на §20 —
   §13.3 показав, що такий гейт працює краще за дисципліну.
6. **Замінити приклад у `deploy/README.md` (П4).**

Пункти 3-6 незалежні один від одного й від приймання на серверах —
кожен можна робити окремим PR. Пункти 1-2 — це відсутність дії, і саме
вона правильна.

## Що лишилось неперевіреним

- Вміст ZIP-ассета draft-релізу `5.3.0-rc.1` не завантажувався й не
  звірявся: для висновку про долю тега це не потрібно, а сам ассет за
  §16.1 не є доказом незмінності.
- Жодного скрипта під Windows PowerShell 5.1 у межах цього аналізу не
  запускалось — середовище не має WinPS. Усі твердження вище отримані з
  вмісту репозиторію, історії Git і GitHub API.
- Питання, чи функціональна розробка 5.3.0 завершена (передумова §8 для
  нарізання RC), тут не вирішується — це рішення власника.
