# Політика маршрутизації AI-моделей

## Мета
Автоматичний розподіл завдань BRAVO-Toolkit між моделями без ручного вибору в кожному запиті. Ця політика не замінює GitHub CI, release gates та авторизацію merge.

## Матриця
| Роль | Модель | Дозволений обсяг |
|---|---|---|
| Основна сесія | Sonnet | Координація повсякденних задач |
| Repository analyst | Haiku | Лише читання, пошук, класифікація |
| Documentation | Haiku | Україномовна документація |
| Developer | Sonnet | Реалізація та тести |
| Test engineer | Sonnet | Тести, регресії, evidence |
| Architect | Opus | Архітектурні рішення та ризики |
| Security reviewer | Opus | Критичне рев'ю без зміни коду |
| Independent reviewer | Codex MCP / окремий Claude | Незалежний review PR |

Модель задається alias у frontmatter агентів; точний model ID та доступність перевіряються в локальному Claude Code. Відсутність Codex MCP не повинна блокувати аналіз: використовуй незалежного Claude reviewer та відзначай fallback.

## Ескалація
LOW — Haiku; MEDIUM — Sonnet; HIGH — Opus (дизайн) + Sonnet (код); CRITICAL — Opus (дизайн та безпека) + Sonnet (код) + незалежний reviewer. Для простого аналізу не запускай Opus без потреби.

## Верифікація
1. Перевір поточний GitHub HEAD та контракт.
2. Зафіксуй ризик, scope та acceptance criteria.
3. Зроби RED/GREEN для дефектів; перевір релевантні тести.
4. Перевір реальні CI jobs, Windows lane та self-test evidence за необхідності.
5. Проведи незалежне рев'ю; не приховуй unresolved P0–P2.
6. Відкрий PR у developer; merge лише за чинними правилами.

## Економія токенів
Передавай мінімально достатні diff, файли й логи; повторно використовуй стабільні інструкції; не дублюй дослідження паралельними агентами. Обліковуй токени, cache reads, тривалість, повторні спроби та вартість прийнятого PR. Цільовий розподіл задач — початкова гіпотеза, не ліміт витрат.

## Перевірка впровадження
- Валідувати JSON конфігурації та frontmatter агентів.
- Перевірити доступність модельних alias на робочій станції.
- Перевірити, що існуючі hooks залишилися без змін.
- Протестувати LOW/MEDIUM/HIGH/CRITICAL сценарії.
- Перевірити Codex MCP і fallback.
- Не стверджувати про успішну маршрутизацію без runtime evidence.
