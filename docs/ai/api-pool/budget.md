# Anthropic API Agent Pool v1: бюджет

Бюджетна підсистема (`ApiPool.Pricing` та `ApiPool.Budget`) гарантує, що сума зафіксованих і ще не звіднених витрат не перевищує глобальний ліміт, а для кожного завдання діє окрема межа. Усі суми обліковуються цілими micro-USD (`[long]`) і округлюються вгору.

## 1. Ліміти і значення за замовчуванням

| Ключ | Значення за замовчуванням | Допустимий діапазон |
|---|---|---|
| `budgetUsd` | 60 | більше 0 і не більше 1000 |
| `perJobUsd` | 2 | більше 0 і не більше 1000; не більше `budgetUsd` |
| `maxConcurrency` | 2 | 1..16 |
| `minRequestIntervalMs` | 250 | 0..60000 |
| `retry.maxAttempts` | 4 | 1..10 |
| `retry.baseDelayMs` | 500 | 0..60000 |
| `retry.maxDelayMs` | 20000 | 0..3600000; не менше `baseDelayMs` |
| `retry.maxRetryAfterSec` | 60 | 0..600 |
| `timeouts.requestTimeoutSec` | 120 | 1..600 |
| `leaseSeconds` | 900 | 30..86400 |

Невідомий ключ конфігурації дає `CONFIG_UNKNOWN_KEY`, значення поза діапазоном: `CONFIG_INVALID`.

Глобальний ліміт у журналі записується записом `INIT` у micro-USD (`budgetUsd * 1 000 000`) разом із `schemaVersion = 1`. Журнал без цього поля (створений раніше) читається як версія 1; будь-яке інше значення дає `LEDGER_CORRUPT` з причиною `unsupported ledger schema`. Повторна ініціалізація з іншим лімітом відхиляється (`CONFIG_INVALID`); з тим самим лімітом є ідемпотентною.

Ефективний ліміт завдання дорівнює мінімуму з усіх значень `perJobLimit`, будь-коли записаних для цього завдання. Тому послаблення `perJobUsd` у конфігурації не збільшує межу вже відомого завдання.

## 2. Ціни

Реєстр моделей: `config/models.json`. Одиниця: USD за мільйон токенів, що дорівнює micro-USD за токен, тому добуток токенів на ціну є точною сумою micro-USD. Обчислення виконуються в `[decimal]`.

`pricesAsOf`: 2026-10-06. Джерело: кеш skill для claude-api; власник повинен перевірити ціни за офіційним прайсом до LIVE.

| Модель | enabled | input | output | cache write 5m | cache write 1h | cache read |
|---|---|---|---|---|---|---|
| `claude-opus-5-5` | так | 4.00 | 20.00 | 5.00 | 8.00 | 0.20 |
| `claude-sonnet-5-5` | так | 2.00 | 10.00 | 2.50 | 4.00 | 0.20 |
| `claude-haiku-5-5` | НІ | див. нижче | | | | |

`claude-haiku-5-5` вимкнено (fail closed): ціну cache read не підтверджено. У файлі наведено два рівні за розміром промпта: до 100K токенів input 0.10 / output 0.50, до 200K токенів input 0.50 / output 2.50 (значення cache write і cache read у файлі лишаються чернетковими). Промпт понад 200K токенів завершується `PRICING_UNKNOWN`. Максимум вихідних токенів для всіх трьох моделей у реєстрі: 128000.

Правила валідації запису моделі: `enabled` булеве; `maxOutputTokens` додатне ціле; `tiers` непорожній масив; кожна ціна більше 0; `cacheWrite1h >= cacheWrite5m >= input`; `maxPromptTokens` строго зростає, `null` дозволено лише в останнього рівня. Невалідна модель позначається в реєстрі `PRICING_INVALID` (це лише маркер запису, він не кидається), а при використанні завершується `PRICING_UNKNOWN`. Невідома, вимкнена або невалідна модель ніколи не має ціни нуль. Реєстр має мати `currency = USD` і `unit = per_million_tokens`, інакше `CONFIG_INVALID`.

Ціни необхідно повторно звірити з офіційним прайсом до переходу в LIVE (див. `operations.md`).

## 3. Верхня межа резервування

Перед кожною спробою резервується верхня межа вартості:

```
inputUpper = байти UTF-8 тіла запиту + 64 + 16 * кількість повідомлень
rate       = max(input, cacheWrite5m, cacheWrite1h) рівня
рівень     = за inputUpper
резерв     = inputUpper * rate + max_tokens * output
```

Кількість токенів не перевищує кількості байтів UTF-8, а константи покривають службове обрамлення. Це припущення справедливе лише для текстових запитів, що забезпечується allowlist запиту.

Приклад для `claude-sonnet-5-5`: тіло 1000 байтів, 1 повідомлення, `max_tokens` 1024:

- `inputUpper = 1000 + 64 + 16 * 1 = 1080`
- `rate = max(2, 2.5, 4) = 4`
- резерв `= 1080 * 4 + 1024 * 10 = 4320 + 10240 = 14560` micro-USD

`max_tokens` більше за `maxOutputTokens` моделі дає `MAX_TOKENS_EXCEEDS_MODEL`; `max_tokens` менше 1: `REQUEST_INVALID`.

## 4. Фактична вартість

Обчислюється з поля `usage` відповіді (`input_tokens`, `output_tokens`, `cache_creation_input_tokens`, `cache_read_input_tokens`). Відсутнє, від'ємне або нецілочисельне значення: `USAGE_INVALID` (адаптер перетворює це на `RESPONSE_MALFORMED` з наслідком `UNRECONCILED`).

- Рівень обирається за повним промптом: `input + cache_creation + cache_read`, де `cache_creation` береться після узгодження (у разі суперечливого розподілу це більша з двох величин, див. нижче), а не зі заявленого поля; цей рівень застосовується до всіх токенів, включно з вихідними.
- Якщо наявний розподіл `cache_creation` на 5m/1h і його сума збігається із `cache_creation_input_tokens`, застосовуються відповідні ціни. Якщо розподілу немає, усе `cache_creation` оцінюється за ціною cache write 1h. Якщо розподіл суперечливий, більша з двох величин оцінюється повністю за ціною 1h.
- Промпт вище найвищого рівня: `PRICING_UNKNOWN`.

## 5. Журнал (ledger)

Файл `<stateRoot>/budget/ledger.jsonl`, append-only, UTF-8 без BOM, один JSON-запис на рядок, завершений `\n`, запис із `Flush`.

Формат запису: `{seq, ts, type, data, prevHash, hash}`; `hash = SHA-256(prevHash + canonicalJson(запис без hash))`. Для першого запису `prevHash` складається з 64 нулів. Канонічний JSON сортує ключі за порядковим порівнянням.

| Тип | Поля `data` |
|---|---|
| `INIT` | `globalLimitMicroUsd` |
| `RESERVE` | `id`, `jobId`, `attemptId`, `amount`, `perJobLimit` |
| `COMMIT` | `id`, `actual`, `evidence` (`requestId`, `messageId`, `usage`) |
| `UNDO` | `id`, `reason` |
| `UNRECONCILED` | `id`, `reason` |
| `RESOLVE` | `id`, `actual`, `evidence`, `reason` |
| `STOP` | `reason` |
| `CLEAR` | `reason` |
| `OVERRUN` | `id`, `reserved`, `actual` |
| `REPAIR` | `reason`, `quarantinePath` |

Кожна операція: узяти `ledger.lock`, виконати повне відтворення журналу з перевіркою ланцюга й `seq`, ухвалити рішення, додати один запис, відпустити замок. Перший запис має бути `INIT`; повторний `INIT` недопустимий.

Стани резервування: `RESERVED`, `COMMITTED`, `UNDONE`, `UNRECONCILED`, `RESOLVED`. `COMMIT`, `UNDO` і `UNRECONCILED` дозволені лише зі стану `RESERVED`; `RESOLVE`: зі `RESERVED` або `UNRECONCILED`. Порушення дає `RESERVATION_STATE_INVALID`, невідомий ідентифікатор: `RESERVATION_NOT_FOUND`.

### Інваріанти

- Під замком: `committed + outstanding (reserved + unreconciled) + нове резервування <= globalLimit`, інакше `BUDGET_EXHAUSTED_GLOBAL`.
- Для завдання сума по всіх його спробах (`reserved`, `unreconciled`, зафіксоване) плюс нове резервування не перевищує ефективного ліміту завдання, інакше `BUDGET_EXHAUSTED_JOB`.
- Доступна сума ніколи не від'ємна (у статусі обмежується нулем).
- `UNDO` можливий лише для відкритого резервування (`RESERVED`); зафіксовані витрати (`COMMITTED`, `RESOLVED`) не скасовуються.

## 6. Обробка результатів спроби

| Подія | Дія | Повтор |
|---|---|---|
| 200 з коректним тілом і `usage` | `COMMIT` з фактичною вартістю | немає |
| 200, тіло некоректне або `usage` непридатне | `UNRECONCILED` (код `RESPONSE_MALFORMED`) | немає |
| HTTP 400, 401, 402, 403, 404, 413, 422 | `UNDO` (код `API_CLIENT_ERROR` або `API_AUTH_FAILED`) | ні |
| HTTP 429 | `UNDO` (`RATE_LIMITED`); `Retry-After` обмежується `maxRetryAfterSec` і зберігається як «не раніше» для моделі | так |
| HTTP 500, 503 | `UNDO` (`API_SERVER_ERROR`) | так |
| HTTP 529 | `UNDO` (`API_OVERLOADED`) | так |
| будь-який інший статус | `UNRECONCILED` (`RESPONSE_MALFORMED`) | ні |
| `TRANSPORT_TIMEOUT`/`TRANSPORT_ERROR` з `sent=false` | `UNDO` | так |
| `TRANSPORT_TIMEOUT`/`TRANSPORT_ERROR` з `sent=true` або без ознаки | `UNRECONCILED` (залишається в обліку) | так |
| інша (не транспортна) помилка під час виклику транспорту | `UNRECONCILED` з кодом цієї помилки | ні |
| непередбачена помилка поза викликом транспорту після резервування | резервування лишається `RESERVED` (в обліку) | ні |

`UNDO` застосовується лише для відповідей, які явно не зараховуються до витрат. Класифікація виконується за HTTP-статусом; наявність `usage` у тілі помилкової відповіді код не аналізує.

Осиротілі резервування (процес завершився між резервуванням і результатом) залишаються в обліку у стані `RESERVED` до ручного звіряння (`budget-reconcile`, розділ 8).

Якщо фактична вартість перевищила резерв, `COMMIT` записується першим (витрату вже враховано), після чого додаються `OVERRUN` і `STOP`, потім пишеться маркер. Адаптер повертає код `BUDGET_OVERRUN` як результат, а не кидає його.

## 7. Аварійна зупинка

Зупинка активна, якщо виконується будь-що одне:

1. існує файл-маркер `<stateRoot>/budget/EMERGENCY_STOP`;
2. у журналі є запис `STOP` без наступного `CLEAR`;
3. похідний стан: є `COMMIT` або `RESOLVE`, де `actual > reserved`, без пізнішого `CLEAR` (захищає від збою процесу між фіксацією перевищення та записом `OVERRUN`/`STOP`).

Поки зупинка активна, нове резервування відхиляється з `BUDGET_STOPPED`.

- `Set-ApiPoolEmergencyStop` спершу записує маркер (навіть коли журнал пошкоджений: зупинка має бути завжди можлива), потім, якщо журнал справний і запису `STOP` ще немає, додає `STOP`. Потрібна причина.
- Перевищення (`COMMIT`/`RESOLVE` з `actual > reserved`) додає `OVERRUN`, `STOP`, потім маркер. Помилка запису маркера не скасовує записів журналу; вона повертається в полі `MarkerError`.
- `Clear-ApiPoolEmergencyStop` спершу видаляє маркер, потім додає `CLEAR`; потрібна причина (порожня відхиляється як `REQUEST_INVALID`). Збій між кроками залишає активним запис `STOP` (безпечний бік). Для пошкодженого журналу очищення відмовляє (`LEDGER_CORRUPT`).

## 8. Звіряння осиротілих резервувань

`Resolve-ApiPoolOrphanReservation` переводить резервування зі `RESERVED` або `UNRECONCILED` у фактичну суму записом `RESOLVE` (потрібні `ReservationId`, сума, причина, за потреби докази). Фактичну суму оператор бере з використання в Anthropic Console за відповідний період. Якщо введена сума більша за резерв, спрацьовує перевищення зі зупинкою (розділ 7).

Автоматичного звіряння немає: резервування лишається врахованим, доки оператор його не звірить.

## 9. Пошкодження і ремонт

Пошкодження (помилка парсингу, розрив ланцюга, прогалина `seq`, невідомий тип, некоректне поле, повторний або відсутній `INIT`, порожній файл, недійсний UTF-8) дає `LEDGER_CORRUPT`: усі резервування відхиляються, операції запису у стані CORRUPT відмовляють (fail closed).

`Repair-ApiPoolLedger` виправляє лише обірваний хвіст: останній рядок без `\n` або останній рядок, що не розбирається (за наявності принаймні одного коректного запису перед ним). Послідовність: копія повного файла в `<stateRoot>/budget/quarantine/ledger-<stamp>.jsonl`, атомарне усічення до останнього коректного запису, повторна перевірка, запис `REPAIR` (причина й шлях до карантину). Якщо після усічення журнал усе ще пошкоджений, повертається `LEDGER_CORRUPT`. Будь-яке інше пошкодження залишається CORRUPT і потребує ручного втручання. Для справного журналу ремонт нічого не робить.

## 10. API стану (Get-ApiPoolBudgetStatus)

| Поле | Значення |
|---|---|
| `State` | `UNINITIALIZED`, `OK`, `STOPPED`, `CORRUPT` |
| `GlobalLimitMicroUsd` | ліміт (null до ініціалізації) |
| `CommittedMicroUsd` | зафіксовані (`COMMITTED` + `RESOLVED`) |
| `ReservedMicroUsd` | відкриті резервування |
| `UnreconciledMicroUsd` | резервування `UNRECONCILED` |
| `AvailableMicroUsd` | ліміт мінус три попередні суми, не менше 0 |
| `EmergencyStop` | `{Active, Reason, Source}`; `Source`: `marker`, `record`, `both`, `derived` |
| `OpenReservations` | `{ReservationId, JobId, AttemptId, AmountMicroUsd, State, Seq}` |
| `LastSeq` | номер останнього запису |
| `CorruptReason` | причина (лише для `CORRUPT`) |

Статус бере замок журналу, коли каталог `budget` існує.

## 11. Обмеження

- Один канонічний корінь стану прив'язує ліміт $60 до одного журналу. Інший корінь стану має окремий журнал і окремий ліміт. Реальною зовнішньою межею є ліміт витрат workspace у Anthropic Console (див. `operations.md`, розділ про LIVE).
- Хеш-ланцюг виявляє випадкове пошкодження, а не втручання того самого користувача ОС.
- Ціни актуальні станом на `pricesAsOf` і підлягають перевірці до LIVE.
