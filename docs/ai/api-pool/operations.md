# Anthropic API Agent Pool v1: експлуатація

Статус: реалізація в процесі (W4); звірити з кодом перед публікацією. (Розділи про CLI, завдання й orchestrate описують проєкт точки входу `Invoke-ApiPool.ps1`, яка ще не потрапила до цієї гілки. Розділи про бюджет, аварійну зупинку та ротацію ключа спираються на реалізовані модулі.)

## 1. CLI

Точка входу: `Tools\ApiPool\Invoke-ApiPool.ps1`, Windows PowerShell 5.1.

```powershell
powershell.exe -NoProfile -File Tools\ApiPool\Invoke-ApiPool.ps1 <команда> [параметри]
```

### 1.1. Команди

| Команда | Призначення | Основні параметри |
|---|---|---|
| `submit` | створити завдання з файлу запиту | `-RequestPath` |
| `run` | виконати створене завдання (синхронно) | `-JobId` |
| `status` | стан завдання | `-JobId` |
| `result` | результат завершеного завдання | `-JobId` |
| `cancel` | позначити завдання скасованим | `-JobId` |
| `resume` | відновити перерване або невдале (retryable) завдання | `-JobId`, `-Reason` |
| `health` | стан пулу: режим, конфігурація, журнал | |
| `capabilities` | можливості збірки: режим, ролі, моделі | |
| `orchestrate` | викликати контракт `apipool.orchestrate/1` | `-RequestPath` |
| `budget-status` | поточний стан бюджету | |
| `budget-init` | створити журнал з лімітом із конфігурації | |
| `budget-stop` | увімкнути аварійну зупинку | `-Reason` |
| `budget-clear` | зняти аварійну зупинку | `-Reason` |
| `budget-reconcile` | звірити осиротіле резервування | `-ReservationId`, `-ActualUsd`, `-Reason` |
| `budget-repair` | відновити обірваний хвіст журналу | `-Reason` |
| `credential-rotate` | записати або замінити ключ | `-SecretPath` |

Спільні параметри: `-StateRoot` (корінь стану; типово `%LOCALAPPDATA%\BRAVO\ApiPool\state`), `-ConfigPath` (файл перевизначення конфігурації).

### 1.2. Вивід і коди завершення

Вивід: один рядок JSON `{ok, code, data}` у stdout. `ok` булеве; `code` відповідає таблиці з `troubleshooting.md` або `OK`.

| Код завершення | Значення |
|---|---|
| 0 | успіх (`ok = true`) |
| 1 | помилка виконання (`ok = false`, `code` описує причину) |
| 2 | неправильне використання (невідома команда, відсутній обов'язковий параметр) |

### 1.3. Поведінка офлайн-збірки

- `run` завершується кодом `MODE_OFFLINE`: без live-транспорту завдання виконати не можна.
- `orchestrate` повертає `status = fallback` з `reasonCode = POOL_DISABLED`; викликач продовжує без пулу.
- Команди `budget-*`, `health`, `capabilities`, `credential-rotate`, `submit`, `status`, `result`, `cancel` працюють локально без мережі.

## 2. Моніторинг бюджету

`budget-status` повертає поля API стану (`budget.md`, розділ 10): `State`, ліміт, зафіксовані, зарезервовані, незвірені, доступна сума, `EmergencyStop`, відкриті резервування. Перевіряйте:

- `State = STOPPED`: активна зупинка (див. розділ 3);
- `State = CORRUPT`: пошкоджений журнал (розділ 5);
- ненульові `UnreconciledMicroUsd` або відкриті резервування, старші за поточні виконання: осиротілі резервування (розділ 4).

## 3. Аварійна зупинка

Увімкнення вручну:

```powershell
powershell.exe -NoProfile -File Tools\ApiPool\Invoke-ApiPool.ps1 budget-stop -Reason "<причина>"
```

Команда записує маркер `budget\EMERGENCY_STOP` (навіть при пошкодженому журналі) і, за справного журналу, запис `STOP`. Нові резервування відхиляються з `BUDGET_STOPPED`.

Автоматична зупинка виникає при перевищенні резерву фактичною вартістю (`OVERRUN`). Перш ніж знімати її, встановіть причину перевищення: перевірте ціни в `models.json`, запис `OVERRUN` у журналі і витрати в Console.

Зняття:

```powershell
powershell.exe -NoProfile -File Tools\ApiPool\Invoke-ApiPool.ps1 budget-clear -Reason "<чому безпечно>"
```

Порожня причина відхиляється. Зняття видаляє маркер і додає `CLEAR`. Якщо журнал пошкоджений, зняття відмовляє: спершу розділ 5.

## 4. Звіряння осиротілих резервувань

Резервування, які залишилися у стані `RESERVED` (процес завершився) або `UNRECONCILED` (невизначений результат), враховуються за повною зарезервованою сумою, доки їх не звірено.

1. Виконайте `budget-status` і випишіть `ReservationId`, `JobId`, `AttemptId`, суму та час (`Seq`).
2. У Anthropic Console відкрийте використання (usage) за період спроби й знайдіть фактичну вартість запиту. Для ключа пулу має бути окремий workspace, щоб не змішувати витрати.
3. Звірте:

```powershell
powershell.exe -NoProfile -File Tools\ApiPool\Invoke-ApiPool.ps1 budget-reconcile -ReservationId <id> -ActualUsd <сума> -Reason "<джерело доказу>"
```

4. Якщо запит у Console не знайдено (не надсилався), сума `0` повертає резерв у доступний бюджет. Робіть це лише з доказом.
5. Якщо введена сума перевищує резерв, спрацьовує аварійна зупинка з `OVERRUN`.

У v1 до LIVE реальних запитів не відбувається, тому осиротілі резервування можуть виникати лише від тестових або fake-прогонів.

## 5. Пошкоджений журнал

`LEDGER_CORRUPT` блокує всі резервування. Порядок дій:

1. Не видаляйте і не редагуйте `ledger.jsonl` вручну.
2. Виконайте `budget-status` і зафіксуйте `CorruptReason`.
3. Якщо причина: обірваний хвіст (незавершений останній рядок), виконайте `budget-repair -Reason "<причина>"`. Копія журналу зберігається в `budget\quarantine\ledger-<stamp>.jsonl`.
4. Будь-яка інша причина (розрив ланцюга, прогалина `seq`, невідомий тип) не ремонтується автоматично. Збережіть файл і зверніться до власника; відновлення виконується вручну з доказів витрат у Console.

## 6. Ротація облікових даних

```powershell
powershell.exe -NoProfile -File Tools\ApiPool\Invoke-ApiPool.ps1 credential-rotate -SecretPath "<абсолютний шлях>"
```

Ключ вводиться через `Read-Host -AsSecureString`; його не слід передавати аргументом. Після успіху: попередній файл збережено як `.previous`, записано `.meta.json` (`rotatedAtUtc`, `fingerprint`), виставлено ACL власника. Старий ключ відкличте в Console. Збій дає `CREDENTIAL_ROTATION_FAILED`. Відкат до попереднього файла виконує функція `Restore-ApiPoolPreviousCredential` (двокрокова, не атомарна заміна; див. `security.md`).

## 7. Перехід OFFLINE -> LIVE

У v1 жодну функцію не можна перемкнути в live лише конфігурацією: `mode = live` відхиляється (`LIVE_DISABLED_IN_BUILD`), а live-транспорт не постачається. Перехід є окремою, керованою рішеннями процедурою. Не пропускайте кроків і не змінюйте їх порядок.

1. Окреме явне рішення власника про перехід у LIVE. Вердикт будь-якого gate, прийняття RC чи цей документ не є таким рішенням.
2. Рішення власника щодо:
   - передавання даних назовні: який вміст репозиторію дозволено надсилати до Anthropic; діє правило проєкту про відсутність реальних ідентифікаторів (імен людей, IP-адрес, імен хостів, назв організацій, облікових записів, кодів ЄДРПОУ, реальних імен файлів із серверів);
   - єдиного канонічного кореня стану: ліміт $60 прив'язаний до одного журналу.
3. Зовнішні обмеження витрат в Anthropic Console, налаштовані й перевірені: окремий workspace і окремий ключ лише для пулу; ліміт витрат workspace не більше $60. Це реальна зовнішня межа; журнал пулу є другою, внутрішньою межею.
4. Звірка цін з офіційним прайсом; оновлення `config/models.json` (зокрема `pricesAsOf`); окреме рішення щодо `claude-haiku-5-5` (увімкнути лише після підтвердження ціни cache read і рівнів).
5. Окремий PR із рецензованим live-транспортом. Обов'язкові рев'ю: codex-qa, codex-security, codex-architecture. Виняток зі статичного сканування мережевих конструкцій обмежується модулем Transport; облікові дані розв'язуються лише всередині самої відправки (live send). Заморожений набір файлів (`architecture.md`) діє: новий `.ps1`/`.psm1` не додається.
6. Власник виконує злиття. Значення `mode = live` встановлюється лише в конфігурації власника.
7. Перший живий smoke-тест лише за явним схваленням власника: мінімальний `max_tokens`, один запит; обов'язкове порівняння запису журналу з даними Console (сума, `requestId`).
8. Відкат: `budget-stop`, повернути `mode = offline`, відкликати ключ у Console.

Статус: реалізація в процесі (W4); звірити з кодом перед публікацією. (Крок 5 описує майбутній PR; код live-транспорту в v1 відсутній.)

## 8. Типові операційні перевірки перед роботою

1. `health` і `capabilities`: режим `offline`.
2. `budget-status`: `State = OK`, немає відкритих осиротілих резервувань.
3. Тести: `Tools\ApiPool\tests\Invoke-ApiPoolTests.ps1` (див. `testing.md`).
