# Anthropic API Agent Pool v1: тестування

Набір тестів автономний, офлайн і не залежить від `BRAVO_SELF_TEST.ps1`. Лише Windows PowerShell 5.1.

## 1. Запуск

```powershell
powershell.exe -NoProfile -File Tools\ApiPool\tests\Invoke-ApiPoolTests.ps1
powershell.exe -NoProfile -File Tools\ApiPool\tests\Invoke-ApiPoolTests.ps1 -Suite Budget,Pricing
```

Параметр `-Suite` приймає імена наборів (імена файлів `suites\<Name>.Tests.ps1` без суфікса). Невідоме ім'я позначається збоєм `Runner/UnknownSuite:<Name>`. Підсумок виводиться рядком `Total: N  Failures: M`. Код завершення 0 лише коли `Failures = 0` і жоден набір не завершився виключенням; інакше 1.

Запуск одного набору не рівноцінний повному запуску: для висновку про готовність виконуйте повний набір.

Статус: реалізація в процесі (W4); звірити з кодом перед публікацією. (Цей рядок стосується лише імпорту модулів `Agents` і `Jobs` та наборів для них: у цій гілці runner імпортує модулі `Core`, `Credentials`, `Pricing`, `Budget`, `Transport`, `Adapter`.)

## 2. Набори

| Набір | Що доводить |
|---|---|
| `Core` | редагування секретів у всіх формах; структуровані помилки і `Get-ApiPoolErrorCode`; завантаження конфігурації (поточна, відсутні ключі, недійсні значення, невідомі ключі); guard шляхів і контекст; атомарний запис; надійний допис рядка; файлові замки (включно з аварійним завершенням утримувача); хешування й канонічний JSON; статичні гарантії щодо файлів, що постачаються |
| `Credentials` | відсутній, порожній, пошкоджений файл; повний цикл DPAPI у sandbox; entropy; перевірка формату; ротація (`.previous`, `.meta.json`, стабільний fingerprint); ACL лише власника; guard `SecretPath`; відсутність відкритого тексту в об'єктах і повідомленнях; редагування зареєстрованих секретів; mock-провайдер |
| `Pricing` | валідація реєстру; точна фактична вартість у micro-USD (кеш, рівні, 5m/1h); верхня межа резервування, округлення вгору |
| `Budget` | ініціалізація; облік; вичерпання рівно на ліміті; ліміт завдання між спробами; неможливість від'ємного балансу; аварійна зупинка; перевищення і автоматична зупинка (включно з неможливістю записати маркер та збоєм після `COMMIT`); автомат станів резервування; збій між резервуванням і фіксацією; перезапуск процесу (новий `powershell.exe`); пошкоджений журнал і ремонт обірваного хвоста; годинник, редагування, таймаут замка |
| `BudgetConcurrency` | змагання окремих процесів за один журнал (розділ 4) |
| `Transport` | live-транспорт не конструюється; fake записує виклики без значень заголовків; вичерпана черга; сценарні збої; облікові дані ніколи не розв'язуються; валідація; повідомлення не містять тіла запиту й секретів |
| `Adapter` | затримки повторів; успіх; облік кешу; 429 і `Retry-After`; 500/503/529 з наступним успіхом; вичерпання повторів; неповторювані помилки клієнта; некоректні відповіді 200; таймаути; скасування; відмова на етапі запиту до резервування; бюджетні відмови (повертаються, не кидаються); перевищення; редагування секретів; слоти конкурентності; спільний rate limit |
| `NetworkIsolation` | офлайн-гарантії (розділ 3) |

Набори для `Agents` і `Jobs` додаються в W4 і в цій гілці відсутні.

## 3. Гарантії офлайн-режиму

Runner `Invoke-ApiPoolTests.ps1`:

- затіняє функції `Invoke-WebRequest` і `Invoke-RestMethod` глобальними версіями, що записують спробу в журнал і кидають `NETWORK_FORBIDDEN_IN_TESTS`; наприкінці перевіряється, що спроб було нуль;
- встановлює мертвий проксі `127.0.0.1:9` як `DefaultWebProxy` на час прогону і відновлює його у `finally`;
- обнуляє змінну процесу `ANTHROPIC_API_KEY` і перевіряє, що її не було використано; значення відновлюється наприкінці;
- набір `NetworkIsolation`: статичне сканування модулів і точки входу на мережеві конструкції (перелік у `security.md`) з перевіркою самого сканера, наскрізний прогін у офлайн-режимі через fake-транспорт (нуль спроб web-cmdlet), негативний контроль (затінені cmdlet справді спрацьовують і фіксуються), відмова live-транспорту за довільних аргументів та відмова `mode = live` при створенні контексту.

Тести ніколи не читають і не пишуть `%LOCALAPPDATA%\BRAVO\ApiPool`. Усі каталоги стану створюються в тимчасових sandbox `ApiPoolTests-<guid>` і видаляються у `finally`. Реальні системні шляхи (каталог даних BRAVO, UNC, префікси пристроїв, корінь диска, репозиторій) передаються лише у валідатор шляхів (`Assert-ApiPoolForbiddenPathRejected`) і в статичний сканер наборів, але не в жодну функцію запису. Окрема перевірка в наборі `Credentials` стежить, щоб набори не передавали реальні системні шляхи функціям запису.

Страж безпеки прогону (tripwire) у `ApiPool.TestHarness.ps1` знімає знімки `C:\ProgramData\BRAVO` та проб у корені диска (`C:\x`, `C:\state`, `C:\ApiPool`, `C:\s.dpapi`) до і після прогону та перевіряє незмінність. Підключення до runner виконується в інтеграційній гілці; у цій гілці runner його ще не викликає.

## 4. Конкурентність

Набір `BudgetConcurrency` запускає окремі дочірні процеси `powershell.exe` для 2, 4 і 8 робітників проти одного sandbox-журналу. Ліміт дорівнює 24 резервуванням по 1 USD; кожен робітник виконує більше спроб, ніж потрібно. Очікування для кожного варіанта:

- рівно 24 успішні резервування, усі інші відхилені з `BUDGET_EXHAUSTED_GLOBAL`;
- ідентифікатори резервувань унікальні, сума не перевищує ліміту;
- журнал справний: `seq` послідовні без дублікатів, `Reserved` дорівнює ліміту, доступна сума 0;
- усі дочірні процеси завершились з кодом 0 за 60 с; у разі перевищення таймауту завершується лише процес, запущений цим набором.

## 5. Що тести НЕ доводять

- Ізоляцію мережевого виходу на рівні ОС: доказом може бути лише брандмауер або відсутність мережі.
- Реальний файл DPAPI власника: тести створюють власні файли в sandbox.
- Довговічність запису на NTFS при втраті живлення.
- Приймання на реальному хості власника: тести виконуються лише в sandbox тимчасового каталогу.
- Поведінку з реальним API Anthropic: live-транспорту у v1 немає. Перед LIVE потрібен окремий smoke-тест (`operations.md`, розділ 7).
- Коректність цін: тести перевіряють арифметику, а не відповідність офіційному прайсу.

## 6. CI

Очікується один крок у наявному job статичних перевірок (без нового job і без нового імені required check), офлайн, не більше 3 дочірніх процесів, тривалість до 60 с. Додатково для документації: у `docs` не повинно бути посилань на чати й сесії асистентів (`git grep` має давати порожній результат).
