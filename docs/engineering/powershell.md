# Правила PowerShell

Обсяг: усі `*.ps1`, `*.psm1` і `*.psd1` репозиторію.

## Цільовий рантайм

Продуктовий і тестовий PowerShell-код BRAVO мусить лишатися сумісним з
**Windows PowerShell 5.1**.

- Для запуску PowerShell-перевірок BRAVO використовуй `powershell.exe`.
  Прогін під PowerShell 7 не є доказом для BRAVO-валідації; якщо
  `powershell.exe` недоступний, перевірку позначай як не виконану.
- Не використовуй синтаксис і cmdlet-и, властиві лише PowerShell 7.
  Приклади заборонених конструкцій: `??`, `?.`, тернарний `? :`,
  ланцюжки команд `&&` / `||`, `ForEach-Object -Parallel`,
  `ConvertFrom-Json -AsHashtable`, `Join-Path` з кількома дочірніми
  аргументами, `Get-Error`, `$PSStyle`, блоки `clean {}`.
- Обмеження стосується лише дочірніх PowerShell-процесів. Нативні
  програми (`git`, компілятори, test runner-и тощо) запускаються звичайно,
  коли задача їх потребує.

## Загальні правила

- Визначай цільову версію PowerShell проекту перед використанням версійно-специфічного синтаксису.
- Надавай перевагу cmdlet-ам і структурованим API замість парсингу локалізованого консольного виводу.
- Використовуй `$env:SystemRoot`, `$env:ProgramData` та інші стабільні системні змінні середовища замість жорстко закодованих системних шляхів Windows.
- Для тимчасових файлів/каталогів використовуй `[IO.Path]::GetTempPath()`, а не сирий `$env:TEMP`, як канонічне джерело: на підтримуваних Windows Server-хостах `TEMP` може вказувати на 8.3 short-профільний шлях, що спричиняло провали очищення в Windows PowerShell 5.1; нові тести/фікстури не повинні повторно вносити цю відому проблему сумісності.
- Використовуй `-LiteralPath`, коли шляхи можуть містити символи підстановки.
- Безпечно екрануй шляхи та аргументи зовнішніх команд.
- Використовуй `-ErrorAction Stop` там, де для надійної обробки помилок потрібен виняток.
- Перевіряй `$LASTEXITCODE` після зовнішніх програм, коли їхній успіх впливає на коректність.
- Не покладайся на англомовні лише повідомлення Windows.
- Перевіряй адміністративні привілеї лише тоді, коли операція дійсно їх вимагає.
- Production-скрипти повинні використовувати змістовні exit-коди й корисну діагностику.
- Надавай перевагу ідемпотентним операціям.
- Для деструктивних операцій реалізуй або зберігай dry-run режим, коли це практично.
- Використовуй узгоджені рівні логування, такі як `[INFO]`, `[WARN]`, `[ERROR]`, `[DEBUG]`.
- Не використовуй декоративні emoji в операційних скриптах чи логах, якщо проект уже цього не робить.
- Уникай припущень щодо поточного каталогу викликача; надавай перевагу
  явним шляхам. Зберігай семантику `Set-StrictMode`, масивів, кодування,
  JSON, нативних процесів, `$LASTEXITCODE`, Scheduled Tasks та винятків.

## Кінці рядків і маніфест цілісності

`.gitattributes` задає `eol=crlf`. Нові файли мусять мати CRLF ще до
регенерації `RUNTIME_MANIFEST.json`: файл із LF-кінцями локально
хешується інакше, ніж у свіжому CI-checkout, і CI впаде з порушенням
цілісності на файлі, який локально виглядає незмінним.

## Семантика колекцій BRAVO

- У Windows PowerShell 5.1 pipeline/умовне присвоєння може розгорнути
  єдиний результат у скаляр. Коли значення семантично є колекцією і
  викликачі покладаються на `.Count`, індексацію чи перелічення, явно
  зберігай семантику колекції (наприклад, через `@(...)`).
- Для змін, чутливих до колекцій, тестуй випадки з нуля, одного та
  кількох елементів під `Set-StrictMode -Version 2.0`.
- Не припускай семантику колекцій, JSON, нативних процесів чи помилок
  PowerShell 7, коли підтримуваним рантаймом є Windows PowerShell 5.1.
