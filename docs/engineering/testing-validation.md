# Тестування й валідація

## Після змін

1. Спочатку запусти найвужчу релевантну перевірку.
2. Запусти наявні тести зачепленої області.
3. Запусти lint, перевірку синтаксису чи збірку, коли вони налаштовані.
4. Переглянь фінальний diff.
5. Переконайся, що тимчасової діагностики не лишилось.

Для виправлення багів надавай перевагу регресійному тесту, який
демонструє збій до фіксу й успіх після нього.

Не можна:

- змінювати тести лише для того, щоб некоректна поведінка проходила;
- видаляти падаючі тести без обґрунтування;
- заявляти, що тести пройшли, якщо їх не запускали;
- ігнорувати падіння перевірок, не пов'язаних зі зміною, не повідомивши
  про них.

Якщо для області немає тестів, виконай найсильнішу практичну
детерміновану валідацію й явно назви обмеження.

## Контракт self-test BRAVO

- `./BRAVO_SELF_TEST.ps1 -NoPause` мусить працювати без змін і лишатися
  типовим повним (Full) прогоном.
- Жодного зменшення покриття: не видаляй, не пропускай, не обходь і не
  послаблюй наявні перевірки.
- Жодних понижень `FAIL -> WARN` заради зеленого CI.
- Жодної внутрішньопроцесної паралелізації через runspace-и, `-Parallel`
  чи background job-и. Паралелізм допустимий лише через окремі CI-job-и/
  процеси, де це дозволяє політика репозиторію.
- Не мігруй фреймворк self-test на Pester.
- Структурний рефакторинг тестів мусить зберігати поведінку й починатися
  з характеризаційної базової лінії.
- Перевірка є доказом, лише якщо вона фактично виконувалась. Фіксуй
  точну команду, код завершення й релевантний результат.
- Окремі фрагменти `-Suite` не самодостатні й споживають спільні
  фікстури: прогін одного suite не еквівалентний повному прогону для
  runtime-релевантної зміни.

## Безпека production-стану

Тести й фікстури ніколи не читають і не пишуть реальний production-стан
BRAVO.

- Production-шлях VersionState: `C:\ProgramData\BRAVO\State\BRAVO_VERSION_STATE.json`.
- Тести використовують sandbox-локальні шляхи стану.
- Production-шлях за замовчуванням лишається незмінним, якщо задача явно
  не змінює production-контракт.
- `BRAVO_ALLOW_DOWNGRADE=1` заборонено як обхідний шлях у тестах чи
  реалізації.
- Не чіпай з тестів інших реальних шляхів під `C:\ProgramData\BRAVO\`.

## Регресійні докази для runtime BRAVO

Для виправлення runtime-бага, де практично: відтвори дефект до фіксу,
покажи, що та сама регресія проходить після фіксу, запусти тести
зачепленого домену, а потім повний self-test, якщо зміна може вплинути на
production-поведінку.

Використовуй випадки, відповідні ризику:

- логіка колекцій: 0 / 1 / N результатів;
- конфігурація: поточна / legacy без властивості / некоректне значення;
- персистентний стан: чистий / legacy / перерваний чи частковий / повтор;
- поведінка файлової системи: шляхи з пробілами й не-ASCII, де релевантно.

CI-докази не замінюють acceptance на реальному сервері, коли змінена
поведінка залежить від служб Windows, Task Scheduler, Credential Manager,
семантики завантаження ОС, WinSCP/SFTP, реставрації чи деструктивної
reconciliation. Таку вимогу acceptance називай явно.

## Розрізнення збоїв

Розрізняй runtime-збої, збої тестів, збої acceptance-harness-у, збої
прив'язки доказів та середовищні збої. Не латай runtime-код, щоб
компенсувати дефекти, які існують лише в інструментах валідації.
